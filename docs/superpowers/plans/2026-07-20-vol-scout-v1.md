# vol-scout v1 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development
> (recommended, two-stage review per milestone per the design spec) or
> superpowers:executing-plans to work this plan task-by-task. Steps use checkbox
> (`- [ ]`) syntax for tracking. Every task is self-contained — a fresh subagent with
> no other context should be able to pick up any single task and complete it from
> this document alone.

**Goal:** Answer, honestly and with statistical backing, whether modern ML and
foundation models beat HAR-RV (the econometric standard) at forecasting equity
volatility — plus a one-page contrast chapter showing the same techniques are
useless on daily returns. Portfolio piece; no trading strategy, no PnL claim.

**Source of truth (binding):** `docs/superpowers/specs/2026-07-20-vol-scout-design.md`.
This plan resolves that spec's three open points (robustness-set tickers + OOS
windows, GARCH h=22 aggregation, Chronos-2 raw-vs-log input) — see "Cross-cutting
design decisions" below. Where this plan is silent, the spec governs.

**Architecture:** One repo, `~/private/vol-scout`. `main` never receives
implementation commits — everything happens on `autopilot/work` (created in Task 0).
Milestones M1→M6 build strictly on each other (M5's backtest needs every model from
M2–M4; M6 needs M5's numbers) — no milestone-level parallelism across M2/M3/M4 the
way the ml-lab SOTA plan parallelized independent repos, because all five models
here share one `MODEL_REGISTRY` and one backtest harness. Tasks *within* a milestone
that touch disjoint files can run in parallel (noted per task).

**Tech stack:** uv + pytest + ruff (gate: `uv run pytest -q && uv run ruff check .`),
pandas/numpy (data + proxies), `arch` (GARCH — the one new dependency, justified in
Task M2.3's commit body), lightgbm, `chronos-forecasting>=2.0` (Chronos-2,
`amazon/chronos-2`), scipy (DM/HLN t-distribution — transitive via lightgbm/pandas
already, verify), matplotlib (all charts, static — see M6 note on why no plotly),
streamlit + `streamlit.testing.v1.AppTest`.

**Ground rules (binding for every task):**
1. TDD per task: write the failing test, run it, confirm the failure, then implement.
2. Gate before any "done" claim: `uv run pytest -q && uv run ruff check .` green.
3. Conventional Commits, English, imperative, atomic — one logical change per commit,
   exact commit messages given per task (adjust only if a step's scope genuinely
   changed during implementation).
4. Explicit-path staging (`git add <files>`), never `git add -A`/`.`.
5. Honest-voice rule: a fix makes a claim *more* defensible, never more impressive.
   Differences smaller than their measured spread are ties — say so, don't round up.
6. No API keys anywhere. yfinance and the HF model hub are both key-free for this
   project's usage.
7. Tests are fully offline: no live yfinance calls in tests (fake `PriceProvider` —
   see M1.1), no live HF Hub calls (Chronos-2 weights pre-cached locally before
   running tests — mirrors `timeseries_showdown.foundation`'s tested convention:
   tests DO make a real small forward pass against cached weights, they just never
   hit the network to fetch them).
8. Long compute runs (the M5/M4 backtest jobs) are resumable (append-only CSV +
   skip-already-computed-origin logic) and run detached (`setsid uv run python
   scripts/... &`, redirect to a log file) — never inside a test, never blocking
   the interactive session.
9. Results artifacts (`data/*.csv`, `results/**`) are committed, not gitignored —
   every headline number must trace to a script-regenerable, committed artifact.

## Cross-cutting design decisions (binding, resolve the spec's open points)

Read this section before starting any milestone — M2–M6 all depend on it being
applied consistently. These are this plan's decisions, not re-litigated per task.

### 1. Universe: SPY + 8-name robustness set + 1 Europe ETF

| Ticker | Sector / role | One-line justification |
|---|---|---|
| **SPY** | Broad index (main series) | Literature-standard proxy for "the market"; every headline number in the README is about SPY. |
| AAPL | Technology (mega-cap) | Most liquid single name globally; "normal" large-cap vol regime. |
| NVDA | Technology (semiconductors) | High-beta growth name; stress-tests every model at the high-vol end of the range. |
| JPM | Financials | Systemically important bank; vol regime tied to macro/credit/rate cycles, distinct driver from broad-market beta. |
| XOM | Energy | Integrated oil major; vol driven by commodity shocks, a third distinct driver. |
| JNJ | Health Care | Diversified pharma/consumer-health; defensive, historically low and stable vol. |
| PG | Consumer Staples | Household/personal-care staple; the lowest-vol contrast in the set. |
| AMZN | Consumer Discretionary | E-commerce/cloud mega-cap; liquid, moderate-to-high vol. |
| CAT | Industrials | Heavy machinery; economically cyclical, macro-cycle-driven vol. |
| **VGK** | Europe (developed markets) | Vanguard FTSE Europe ETF — pan-European broad index, the most direct Europe analog to SPY's own role; avoids one single-country ETF's idiosyncrasies. |

All ten are liquid, USD-listed (VGK included), and have traded since well before
`DATA_START` below — no listing-date edge cases to special-case.

### 2. Data window and backtest cadence

- `DATA_START = "2010-01-04"` (first trading day of 2010) — the fetch floor for all
  ten tickers. ~8 years of pre-OOS history for the earliest backtest origin.
- `OOS_START = "2018-01-02"` (first trading day of 2018) — the backtest spans Feb
  2018's vol spike, the Dec 2018 selloff, the 2020 COVID crash, the 2022 hiking
  cycle, and 2023+ — multiple genuinely distinct regimes (mitigates, per the spec's
  honest-limitation #2, but does not solve the one-sample-period problem).
- `STEP_TRADING_DAYS = 5` (weekly re-forecast cadence) — origins tile **forward**
  from `OOS_START` (`OOS_START`, `OOS_START + 5td`, `OOS_START + 10td`, ...), unlike
  `timeseries_showdown.make_windows`'s backward-from-the-end tiling. Forward tiling
  is deliberate here: new trading days arrive continuously, and forward tiling means
  every previously-computed origin's window is byte-identical after a data refresh
  — new origins only ever append at the tail. This is what makes the M5 backtest
  script's skip-already-computed-origin resumability correct across data refreshes.
- `HORIZONS = (1, 22)` (1 trading day, ~1 trading month).
- Origin count: ~(today − 2018-01-02) / 5 trading days ≈ 400+ per ticker as of this
  plan's writing date (2026-07-20) and growing; comfortably above the n≥20 floor
  DM/HLN needs to be trustworthy (see `timeseries_showdown/stats.py`'s own docstring
  on this).

### 3. DM/HLN's `h` parameter — resolves "overlapping h=22 → HAC handling"

Two headline pairs per model comparison, and they need **different** `h` in the DM
test (this is the parameter counting autocovariance lags in the loss differential,
**not** the forecast horizon — see `timeseries_showdown/stats.py`'s module
docstring, same distinction applies here):

- **h=1 pair**: each origin's test window is exactly 1 trading day, and origins are
  ≥5 trading days apart — the target days across origins never overlap. This is
  the textbook non-overlapping case → `dm_test(..., h=1)`, same choice
  `timeseries_showdown` made for its own disjoint windows.
- **h=22 pair**: each origin's test window is 22 trading days, but origins step by
  only 5 → consecutive windows share 17 of 22 days. This is genuine, heavy overlap
  — the classic Diebold-Mariano motivating case for h-step-ahead forecast
  comparison. Use `dm_test(..., h=22)` (the forecast horizon itself), the standard
  prescription for h-step overlapping forecasts (Diebold & Mariano 1995; Harvey,
  Leybourne & Newbold 1997 for the small-sample correction on top of it).

State this explicitly in `stats.py`'s module docstring — a future reader must not
assume "h in dm_test always equals 1" just because that was the right answer in the
sibling project.

### 4. Modeling scale: variance throughout, log-transform for the ML/FM side

- **Every proxy, every model's output, and every metric (QLIKE/RMSE/MZ/DM) operates
  on the variance scale** (squared-return units), never on the volatility
  (std-dev) scale. QLIKE is only well-defined and "robust to proxy noise" for a
  variance target (Patton 2011) — this must not drift.
- **HAR-RV, LightGBM, and Chronos-2 all fit/forecast `log(RV)`**, exponentiating
  predictions back to variance scale before evaluation. This is "log-HAR" — a
  standard, literature-backed variant (Corsi 2009's own follow-on literature), not
  an invented convenience: RV is heavy right-tailed (vol clustering, occasional
  crash-sized spikes) and log-space is much better-behaved for an OLS fit, a GBDT
  target, and a zero-shot foundation model's input distribution alike. This
  resolves the spec's "raw-RV vs log-RV for Chronos-2" open point — log, applied
  consistently across the three models that share this concern.
- **GARCH(1,1) is the one exception, structurally, not by choice**: it is fit
  directly on daily log-returns (not on the RV proxy at all) and its native output
  *is* a conditional-variance forecast — there is no "log-GARCH-RV" equivalent to
  reach for. Its forecast is still evaluated against the same RV-proxy ground
  truth as everything else. Document this asymmetry once, in `models.py`'s module
  docstring, and reference it rather than re-explain it in every task.
- **Random-walk stays on the raw scale** (no transform at all) — it is deliberately
  the simplest possible baseline.

### 5. h=22 target definition and GARCH's h=22 aggregation (resolves that open point)

The h=22 **ground truth** is the sum of the 22 daily RV-proxy values strictly after
the origin — `sum(RV_{o+1 .. o+22})` — never a proxy formula re-applied to a 22-day
OHLC bar (that would discard almost all the intraday information the daily proxies
already captured). This single definition is what every model's h=22 forecast is
built to predict and what QLIKE/RMSE/MZ evaluate against.

- **GARCH → iterated aggregation.** One `arch_model` fit produces a 22-step-ahead
  analytic variance forecast path in a single `.forecast(horizon=22)` call (`arch`
  computes the standard GARCH(1,1) recursion internally — no manual recursion
  needed); h=1 is that path's first step, h=22 is the sum of all 22 steps. This is
  the textbook way to get a multi-day GARCH variance forecast and is *why* GARCH is
  fit on returns rather than the RV proxy directly.
- **HAR-RV and LightGBM → direct.** Two separately-fit models per origin (one
  targeting `log(RV_{o+1})`, one targeting `log(sum(RV_{o+1..o+22}))`), matching
  this project's own established "direct, no recursion" convention for regression
  models (mirrors `timeseries_showdown.baselines.forecast_lgbm`'s docstring on the
  same choice) — avoids compounding a 1-day model's own forecast error 22 times.
- **Chronos-2 → direct, one call.** `predict_quantiles(..., prediction_length=22)`
  in one shot (Chronos-2's own `model_prediction_length` is 1024, per the sibling
  project's verified finding — no library-internal chunking at 22 steps); h=1 =
  day-1 median, h=22 = sum of all 22 days' medians (a standard, if approximate, way
  to get a cumulative point forecast from a foundation model without needing joint
  quantile machinery — documented as an approximation, not hidden).
- **Random-walk → h=1 is `RV_o`; h=22 is `22 * RV_o`** (today's daily variance
  level held constant and summed over the horizon).

### 6. Model registry contract (`models.py`)

```python
@dataclass
class ForecastResult:
    point: dict[int, float]       # {1: rv_hat_h1, 22: rv_hat_h22} — VARIANCE scale
    fit_predict_seconds: float

MODEL_REGISTRY: dict[str, Callable[[pd.DataFrame], ForecastResult]]
```

One call per model per origin, `train_df` already sliced to everything known as of
that origin (mirrors `BacktestWindow.train_slice`). Every model returns **both**
horizons from that one call — this is simpler than `timeseries_showdown`'s registry
(which had to support quantiles + optional covariates); vol-scout needs neither
(QLIKE/RMSE/MZ are point-forecast metrics only, no calibration/coverage figures in
this spec). HAR-RV/LightGBM fit twice internally inside that one call (once per
horizon's own target); GARCH/Chronos-2/random-walk fit once and derive both
horizons from the same forecast path.

### 7. Persistence contracts

- `data/<TICKER>.csv`: columns `date, open, high, low, close, volume` (yfinance
  `auto_adjust=True` back-adjusted OHLC — same caveat `signal-trader-demo`'s
  provider documents: restated for later splits/dividends, kept anyway, free and
  simple, documented not hidden).
- `results/forecasts.csv`: **one file, long format, every model/ticker/origin/
  horizon** — columns `model, ticker, origin, horizon, rv_true, rv_pred,
  fit_predict_seconds`. One shared file (not per-model, unlike
  `timeseries_showdown`) because this project has 10 tickers × 5 models × 2
  horizons × ~400 origins — a per-model-per-ticker file split would be 50+ files
  for no benefit. Append-only; the M5/M4 compute scripts skip `(model, ticker,
  origin)` triples already present.
- `results/metrics.json`: `{"<model>": {"<ticker>": {"h1": {...}, "h22": {...}}},
  ..., "headline": {"<model_a>_vs_<model_b>": {"h1": {...dm...}, "h22": {...dm...}}},
  "meta": {...}}`. Per-(model, ticker, horizon) bucket: `QLIKE`, `RMSE`,
  `QLIKE_std/min/max` (per-window spread), `MZ` (Mincer-Zarnowitz intercept/slope/
  R²), `mean_fit_predict_seconds`. `headline` carries `dm_test`/tie-verdict results
  for the pairs the README leads with (every model vs. HAR-RV, on SPY).

### Task M1.2: Volatility proxies + multi-day RV aggregation

**Files:** Modify `src/vol_scout/data.py`, `tests/test_data.py`

- [ ] **Step 1: Write failing tests, hand-computed.** On a tiny synthetic
  4-5-row OHLC frame (values chosen so you can compute the expected numbers by
  hand — do the arithmetic in the test file, same style as
  `test_backtest.py::test_evaluate_forecast_hand_computed`):
  - `parkinson_rv(df)`: `(1/(4*ln2)) * ln(H/L)^2` per row.
  - `garman_klass_rv(df)`: `0.5*ln(H/L)^2 - (2*ln2 - 1)*ln(C/O)^2` per row.
  - `squared_return_rv(df)`: `ln(C_t/C_{t-1})^2` (first row is NaN — no prior close).
  - `log_return(df)`: `ln(C_t/C_{t-1})` (needed by GARCH in M2.3; document that
    `squared_return_rv` is literally `log_return**2` — one definition, not two).
  - **A sensitivity-illustrating test**: construct one row with a big intraday
    range but a nearly-flat close-to-close move, and one row with a big
    close-to-close move but a narrow intraday range — assert
    `parkinson_rv`/`garman_klass_rv` >> `squared_return_rv` on the first row and
    the reverse on the second. This is the test that *demonstrates* honest
    limitation #1 (why multiple proxies matter), not just checks arithmetic.
  - `multi_day_rv(daily_rv: pd.Series, days: int) -> pd.Series`: trailing rolling
    sum (`daily_rv.rolling(days).sum()`) — a dumb primitive; hand-verify on a
    5-value series that `multi_day_rv(s, 3).iloc[2] == s.iloc[0]+s.iloc[1]+s.iloc[2]`
    and the first two entries are NaN.
- [ ] **Step 2: Run tests, verify they fail.**
- [ ] **Step 3: Implement** the four functions above in `data.py`. Keep
  `multi_day_rv` deliberately dumb (no forward/backward shifting) — M2/M3/M5's
  target-builders are responsible for shifting it correctly into a forecast
  target, exactly the separation-of-concerns `timeseries_showdown.baselines
  ._rolling_as_of_origin` uses (low-level primitive vs. caller-side alignment).
- [ ] **Step 4: Gate green.**
